# 完成任务后的规格同步

当实现工作已经完成，需要把最终决策记录回仓库时使用本 skill。固定顺序是：**先完成任务，再执行文档同步流程**。

## 工作约束

- 默认在当前仓库工作，除非用户明确指定其他仓库。
- 写入前必须读取适用的 `AGENTS.md`、`specs/mission.md`、`specs/tech-stack.md`、`specs/roadmap.md`、相关已完成 phase 的产物，以及 `templates/requirements.md`、`templates/plan.md`、`templates/validation.md`。
- 不修改源代码、测试、依赖、CI 配置或无关文档。通常只允许写入 `specs/` 和 `CHANGELOG.md`。
- 不得臆造实现事实。依据当前分支的 diff、提交记录、测试结果和用户提供的完成证据进行同步。工作区有未提交修改本身不代表任务未完成。
- 如果仓库或任务完成证据不可用，停止并要求用户上传缺失产物，不要猜测。可接受的交接材料包括任务/设计变化、实现摘要或提交 ID、验证输出，以及最终产品或架构说明。如果仓库中已有这些内容，不要要求用户重复上传。
- 保持 skill 可被正常发现。除非用户明确指定提交或外部上传目标，否则不要执行 git commit，也不要上传到外部服务。Git commit 和远端 push 是两个独立动作：用户只说“提交”时只提交，用户明确说“上传/推送”且远端和分支明确时才 push。

## 必须先预览，再执行

每次运行分为两个阶段：

1. **预览阶段。** 检查仓库并报告：
   - 实现任务已经完成的证据；
   - `specs/roadmap.md` 中找到的下一个未完成 phase；
   - 准备创建或修改的确切文件；
   - 每个文件的简短变更摘要；
   - 计划使用的日期、feature 名称和完成状态；
   - 计划执行的 Git 动作（暂存、commit、push 分开列出）；
   - 需要用户上传的缺失产物。

   此阶段不要写入文件。请用户确认文件清单和变更内容后再继续。如果 roadmap 中存在多个合理的下一个 phase，或现有 feature 目录可能对应其他 phase，必须暂停询问，不要静默选择。用户明确要求“完整同步已完成任务”时，预览必须同时包含三份顶层 specs、指定日期 feature 目录中的三个文件和 `CHANGELOG.md`；不能因为现有 roadmap 已全部完成而省略 feature 目录。

2. **执行阶段。** 只有在用户明确确认后，才创建或更新已批准的文件，执行下面的验证，并展示最终交接清单。如果用户要求提交，先检查是否存在无关的已暂存修改，只暂存本次生成的文档文件，然后使用简短提交信息，例如 `docs: sync phase specs and changelog`。否则保持未提交，并明确说明。

## 发现仓库并选择 phase

1. 定位仓库根目录，检查工作区状态、当前分支和提交历史。
2. 读取现有 specs 和模板。保留项目已有的术语、标题、状态标记和写作风格。
3. 按 roadmap 顺序找到第一个未标记完成的 phase。识别仓库已有的完成约定，例如 `[ ]`/`[x]`、状态词或同等写法。
   - 如果存在未完成 phase，按 roadmap 选择它，并在执行完成后标记为完成。
   - 如果所有 phase 都已完成，但用户明确要求同步当前已完成任务，则把当前任务作为新的已完成 phase 记录到 roadmap；不要臆造未来 phase，也不要因为没有“下一个 phase”而跳过 feature spec。
   - 如果用户只要求普通预览而没有要求同步已完成任务，报告没有下一个 phase，并停止在预览阶段。
   - 如果 roadmap 没有清晰的状态约定，报告歧义并在编辑前请求确认。
4. 根据待同步任务生成小写 kebab-case feature 名称，并使用当前本地日期：`specs/YYYY-MM-DD-feature-name/`。
   - 已完成任务的 feature 目录仍然必须包含 `requirements.md`、`plan.md`、`validation.md`，并在文件中明确记录“✅ 已完成”及其证据。
   - 如果目录已经明确对应同一个任务，先展示计划再更新；如果目录存在但对应其他内容，不要覆盖，报告冲突并请求决定。

## 需要生成或更新的文件

### 顶层 specs

只更新受影响的顶层 spec。用户明确要求“同步 specs 三个文件”时，必须逐一检查并在 preview 中说明是否修改：

- `specs/mission.md`：产品使命、用户价值、成功边界或非目标发生变化。
- `specs/tech-stack.md`：架构、运行时、框架、依赖、集成、数据或部署决策发生变化。
- `specs/roadmap.md`：选定 phase 的范围、状态、顺序、依赖或完成标记发生变化。

对于 mission，不能塞入实现细节，只记录用户价值或可观察的成功标准；对于 tech-stack，只记录实际采用的技术或约束；对于 roadmap，记录任务目标、日期和完成状态。每一处拟议修改都必须能追溯到已完成任务的具体证据，不要重写未受影响的章节。若某个顶层文件经检查确实不受影响，应在 preview 中列出“检查后不修改”，不能静默遗漏。

### Feature spec 目录

除非用户明确批准额外文件，否则在选定或新建的任务目录中只创建以下文件：

- `requirements.md`：上下文/证据、范围内行为、范围外行为、约束、决策、假设和可观察的验收预期。
- `plan.md`：按需求拆分 task group，并按依赖关系和实现顺序排列。必要时加入验证任务，但不要添加推测性工作。
- `validation.md`：自动化检查、场景验证、与该 phase 相关的边界情况，以及明确的完成条件。

先读取 `templates/requirements.md`、`templates/plan.md`、`templates/validation.md`；如果本次要修改三份顶层 specs，再读取对应的 `templates/mission.md`、`templates/tech-stack.md`、`templates/roadmap.md`。结合项目实际情况改写，删除模板占位符，不要复制通用填充内容。feature spec 记录的是已经完成的任务及其决策，因此必须与实现和测试一致，而不是描述想象中的未来设计。

### `CHANGELOG.md`

根据当前分支的 git 提交生成或更新：

- 按提交日期分组，最新日期在前。
- 每个提交添加一条简短 bullet，并包含短 hash，便于后续运行去重。
- 保留既有条目和格式，只在对应日期分组中补充缺失的提交。
- 摘要必须客观、简短。不要暴露密钥，也不要粘贴完整提交信息。
- 如果旧 changelog 没有 hash，在日期/主题匹配可靠时用于去重；历史条目无法明确匹配时，保留原文，不要重写。

文档验证成功后，使用 roadmap 既有语法将选定或新建的任务 phase 标记为完成。新建任务必须同时在 roadmap、`plan.md` 和 `validation.md` 中保持一致的完成状态。不要标记其他 phase。

## 验证与交接

针对这次仅涉及文档的变更，执行相称的检查：

- 确认 `requirements.md`、`plan.md` 和 `validation.md` 存在且非空；
- 确认选定或新建任务已标记完成，并且没有无意修改其他 phase；
- 确认新增或修改的 changelog 条目按日期分组、最新在前，并且每个新记录的提交只有一条 bullet；
- 运行 `git diff --check`；
- 检查 `git diff --name-only` 和完整 diff，确保没有源代码或无关文件变化；
- 如果仓库已经定义了文档/spec 检查，则运行这些检查；不要为本流程凭空创建一套大范围测试。

最后输出交接清单，列出所有生成/更新的文件和已经执行的检查。如果用户要求提交，确认只暂存本次文档文件并报告 commit hash；如果用户要求上传/推送，列出准确的远端、分支和文件，并说明是否真的完成。没有已配置且获授权的目标时，不得声称已经完成外部上传。如果用户仍需提供输入，列出缺失文件并暂停。
